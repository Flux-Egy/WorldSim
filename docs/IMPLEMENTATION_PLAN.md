## Assemblies

```
WorldSim.Core          pure C#, noEngineReferences. PRNGs, seeds, hashing, tile structs,
                     binary save codec. Blittable and Burst-callable. Unit-testable without Unity.
WorldSim.Simulation    DOTS: components, ISystem/IJob, worldgen jobs, AI, pathfinding,
                     civ layer, economy, disasters. Refs Core, Entities, Burst, Collections, Mathematics.
WorldSim.ModAPI        PUBLIC, stable. Definitions, registries, event hooks. Refs UnityEngine
                     only (sprites, UI). Never references Simulation or Entities.
WorldSim.Modding       Internal bridge: loader, manifest validation, ModAPI -> DOTS blob/registry
                     translation, mod hash logging, signature check.
WorldSim.Presentation  MonoBehaviours: camera rig, touch input, terrain/unit renderers,
                     UI controllers, settings, bootstrap. Refs Simulation, ModAPI, Modding.
WorldSim.Editor        Build profiles (Release / Modder), project setup, scene creation.
WorldSim.Tests.EditMode / WorldSim.Tests.PlayMode   determinism, save round-trip, mod tests, stress.
Samples~/SampleMod   class library compiled against WorldSim.ModAPI.dll only.
```

Rule: Burst cannot compile code that is loaded at runtime, so **mod code never runs inside jobs**. Mods register *data* (definitions, curves and effect parameters), which WorldSim.Modding converts into blittable tables that the existing Burst systems read. Mod C# runs on the main thread, for event hooks and UI only.

## Scenes

`Boot.unity` (settings, mod scan, ECS world) → `MainMenu.unity` (new or load world, Mods menu, Settings) → `World.unity` (camera rig, renderers, HUD). The scenes are generated by `WorldSim > Setup > Create Scenes` because I can't reliably hand-write scene YAML.

## Requirements I cannot meet as written, and the alternatives I propose

1. **Mod loader (§9.2, §18.1).** MelonLoader 0.7.3 (May 2026) ships Windows, Linux and macOS builds only, with no Android build. LemonLoader's last release was 0.6.5.1 (March 2025), and it works by *patching an installed APK*. Both are built for injecting into games you don't own, not for integrating into your own game.
   An Android Mono "Modder" build has its own problem. **To my knowledge** Unity's Mono backend on Android targets ARMv7 only (ARM64 requires IL2CPP; to be confirmed in Player Settings). Recent flagships, such as Pixel 7 and later, cannot run 32-bit apps at all.
   **Proposal:** a first-party loader plus **HybridCLR** (MIT, actively maintained, documents support for 6000.x), which adds an interpreter to IL2CPP so `Assembly.Load(bytes)` works on IL2CPP ARM64. That gives one shippable build that supports mods. The Release/Modder split in §18.1 then becomes "verbose loader logging on/off", and the ModAPI surface stays identical. Fallback if HybridCLR is rejected: keep §18.1 literally (a Mono ARMv7 Modder build), and release players get *data-only* mods (JSON definitions + sprites) without DLLs.
2. **Cross-device determinism (§4.3).** Burst does not guarantee identical float results across x64 and ARM64. Worldgen noise and anything that feeds the world hash therefore use **integer and fixed-point math**. Floats are allowed only in presentation code.
3. **Render scale 0.75× and 1.5× (§7.2) vs Pixel Perfect (§3.1).** Non-integer scales cannot be pixel-perfect. Proposal: 1× and 2× use the Pixel Perfect Camera at integer zoom. 0.5×, 0.75× and 1.5× render to a lower or higher internal resolution and switch on Pixel Perfect's "stretch fill" mode (some shimmer, labelled in the UI).
4. **Anti-aliasing (§7.2).** FXAA and SMAA exist in URP but blur pixel art. I'll keep the option with the default set to Off, and note in the UI that it softens pixels.
5. **2D shadows on thousands of units (§7.2).** `ShadowCaster2D` per unit isn't viable on mobile. Proposal: real 2D shadows on structures only, and a baked drop-shadow sprite for units.
6. **SRP Batcher + GPU Instancing (§3.1).** These don't combine on one draw: when a shader is SRP Batcher compatible, the SRP Batcher takes precedence. Proposal: the SRP Batcher for terrain and UI, and explicit `RenderMeshInstanced` calls for units (which also bypasses that precedence).
7. **Mods registering by `byte biomeId` (§9.3).** Two mods would collide on IDs. Proposal: mods register by string key (`"mymod:lava"`), the runtime assigns the byte, and the mapping is stored in the save's mod registry section.
8. **LZ4 (§10.2).** Not available in .NET Standard. I'll use GZipStream. LZ4 is possible later via K4os.Compression.LZ4 (MIT) if profiling shows the need.
9. **"Android Systrace" (§13.3).** Systrace is deprecated, so I'll document Perfetto instead.
10. **Two-finger rotate (§8.1, optional).** Rotating a pixel-perfect orthographic view breaks pixel alignment. Deferred.
11. **ARMv7 (§13.2).** Google Play requires 64-bit and §2.1 targets modern phones, so Release is ARM64 only.

12. **Noise algorithm (§4.2).** OpenSimplex2/Simplex reference code is floating point. World generation uses **Q16.16 fixed-point gradient noise** (quintic fade, 8 gradients, fBm, domain warp), which plays the same role and is bit-identical on every CPU. Golden world hashes in `WorldGenTests` lock this down.
13. **Terrain rendering (§7.3) in Stage 2.** There's no art yet, so the terrain is a Burst-painted texture (4×4 procedural pixels per tile) on one SpriteRenderer, with a Global Light2D (URP 17.3 clears the 2D light texture to black without one). The biome-blend shader and atlas arrive with real tile art.
14. **Pixel Perfect Camera vs free pinch zoom (§3.1, §8.2).** The Pixel Perfect Camera sets `orthographicSize` itself, so it's disabled while free zoom is in use. Integer-step pixel-perfect zoom returns with the graphics settings (§7.2, item 3).
